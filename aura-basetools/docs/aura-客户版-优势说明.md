# Aura 文件读写工具 —— 相对原生 read / write / edit 的能力说明

**适用读者**：评估「让 AI 编码助手在真实代码库里改文件」这件事的技术决策者与研发负责人。
**一句话**：原生文件工具在**文本层**工作（读进来、归一化、写回去）；Aura 在**字节层**工作
（只改你指到的地方，其余字节原样不动），并把「改哪儿、改前该是什么、改完是否真是那样」变成可预演、
可校验、可拒绝的结构化流程。

---

## 一、结论（30 秒）

| # | 原生 read / write / edit 的常见行为 | Aura 的做法 | 你能感知到什么 |
| --- | --- | --- | --- |
| 1 | 编辑时可能按"多数风格"重排整份文件的行尾、并丢掉 UTF-8 BOM | 逐字节写回，只改被指到的区域 | **diff 里只有你真正改的东西**，不再出现"改 1 行、动 900 行" |
| 2 | 只能按字面文本替换：必须先把原文一字不差地读出来 | 四层寻址（符号名 / 行号 / 唯一词 / 记忆原文），不必先抄准原文 | 少读、少错、少来回 |
| 3 | 并发改动靠整份版本比对：别人改了无关位置也会挡住你 | 区域级新鲜度检查 + 写盘前版本校验 | 只在你真正要改的那块被改过时才拦，并**告诉你重读哪几行** |
| 4 | 写完即结束 | 落盘后把文件读回来逐字节校验 | 回执里带 `write_verify`，不是"相信它成功了" |
| 5 | 一处一处改，中途失败留半成品 | 一次调用多处修改，**任一不成立则磁盘完全不变**；支持预演 | 失败是"什么都没发生"，不是"改了一半" |
| 6 | 读就是整份读 | 七种取景：符号目录 / 接口 / 窗口 / 搜索 / 差异 … | 同一文件上下文占用约 **1/24**（实测见 §二） |

**适用范围**：让 AI 助手在真实工程里读代码、改代码——要求 review 干净、CI 稳定、多人多助手并行的场景。
**不适用**：整份重写（用原生 `write`）、读取图片（用原生 `read_image`）、二进制文件、单 `\r` 老式行尾。
**不替换任何原生工具**：Aura 与它们并存，按场景分工（见 §四）。

## 二、它解决的三类事故

这三类事故的共同点是：**工具回执说"成功"，没有任何报错**，代价要到 code review、CI 或事故复盘时才出现。

### 事故 A：只改一行，diff 变成整份

**现象**：在一个 CRLF 行尾的文件里改了 1 行，提交上去发现整份文件的每一行都变了。
**代价**：`git blame` 全部失效、每条分支都冲突、CI 的行尾/格式检查全红、评审无法看清真实改动。
**原因**：这类工具在编辑前会把内容"规范化"（`\r\n` 统一成 `\n`），再按文件里**占多数**的行尾风格
整份重排写回。这是文本层工具的通用设计，不是某个产品的偶发缺陷。

**对照实验**（同一改动：把第 2 行 `const b = 2;` 改成 `const b = 22;`；文件 54 字节，第 1、4 行 CRLF）：

| | 原生 `edit` | Aura |
| --- | --- | --- |
| 文件字节数 | 54 → **53** | 54 → **55**（正好 +1，就是这次改动） |
| 行尾 | CRLF×2 → **0**（全变 LF） | CRLF **仍是 2**，LF **仍是 2** |
| 未改动的行 | 第 1、4 行**被重写** | **一字未动** |

### 事故 B：编码被改，没人报错

**现象**：一份带 UTF-8 BOM 的文件被编辑后，BOM 消失；下游工具（部分构建链、导出的 CSV、做文件哈希校验的流程）
报编码异常或产生假变更。
**代价**：故障点离改动点很远，排查成本高；BOM 丢了再补上，也是静默的。

**对照实验**（同一改动；文件 29 字节，以 `EF BB BF` 开头）：

| | 原生 `edit` | Aura |
| --- | --- | --- |
| 文件字节数 | 29 → **27** | 29 → **30**（正好 +1） |
| 开头 3 字节 | **变成 `63 6f 6e`（BOM 消失）** | 仍是 `ef bb bf`（BOM 保留） |

### 事故 C：并发改同一文件

**多助手 / 多人同时改**是 AI 编码的常态。

- 原生工具的并发保护是**整份版本比对**：这是有效的保护，但它（1）粒度粗——别人改了文件里任何无关位置，
  你这条合法修改也会被挡；（2）提示信息不指向具体位置，你只能把整份重读一遍（再付一次整份上下文）。
- Aura 是**区域级**的：只有你指到的那块在你上次读之后变过，才拒绝，并在回执里**指名行号**：

```
{ "ok": false, "code": "PATCH_STALE_REGION",
  "error": "… the addressed region (lines 1-1) changed after the last observation — re-read those lines, then retry" }
```

「重读那几行」而不是「重读整份」，这是并行场景里省下的主要成本。

## 三、六项能力（每项都能在回执里看到）

| 能力 | 说明 | 回执证据 |
| --- | --- | --- |
| **1 逐字节保真** | 前导 BOM 的数量、每一行各自的行尾风格都原样保留；只改被寻址的字节 | `write_verify: {level:"bytes", bytes:42}` |
| **2 四层寻址** | `target`（符号名）/ `lines`（行号区间）/ `line_cue`（该行唯一的词）/ `anchor`（记忆的原文，容忍空白漂移） | 成功回执带 `tier:"symbol"`、`line`、`actual`（它实际找到的原文）、`near` |
| **3 落位可断言** | `expect`：先断言"这里应该是这段"，对不上则整批失败；`dry_run`：只定位不落盘 | `ok:false` + 明确 code，磁盘不变 |
| **4 并发安全** | 区域级新鲜度 + 写盘时版本校验；歧义则拒绝而非猜 | `PATCH_STALE_REGION`、`LOCATOR_CUE_AMBIGUOUS`（`"value" appears on 2 lines`） |
| **5 原子与自证** | 多 hunk 一次落盘，任一不定位则磁盘完全不变；落盘后回读校验 | 见上 `write_verify` |
| **6 按意图取景** | `map` 符号目录 / `digest` 只要接口 / `around` 开窗 / `lines` / `search` / `changed` 差异 / `full`；65 种源码扩展名有符号表（数字由引擎语言表决定，随版本增长） | 回执带 `version` 令牌与 `next` 建议 |

**上下文成本实测**：一个 84.8 KB、1,848 行、204 个符号的源文件——
`map` 回执 3,555 字符（**4.2%**，65 个符号带行号）、`digest` 回执 2,885 字符（**3.4%**）。
换句话说：**一次结构性阅读，上下文占用约为整份读入的 1/24**。

**失败可见性**：每次调用都返回一条结构化回执（`ok` / `code` / `error` / 建议）。我们针对 MCP 接口
专门做了坏输入验证：参数名写错、模式写错、文件不存在、参数类型不对、未知工具、以及"连续 5 次坏输入之后
再正常调用"——6/6 都返回可读错误，服务不中断。对使用者意味着：AI 助手能**自己读懂错在哪并纠正**，
而不是卡住或反复试。

## 四、与原生工具共存（引入风险接近零）

- **不替换、不停用**任何原生工具。原生 `read` / `edit` 与读图能力都保留。
- **整份重写用 `aura_basetools_write`**：新建/覆写、BOM 与文件既有行尾保留、事务/undo；覆写默认
  要求先读过这一版（与原生 `write` 的 read-before-write 同形），`--allow-unobserved` 才是
  显式盲写。避免“随手全量覆盖”这类高危操作。
- **读图仍用原生 `read_image`**：Aura 没有替代品，我们也不会去停用它。
- 推荐默认分工：**改文件优先 Aura（局部用 `aura_basetools_edit`，整份定稿用 `aura_basetools_write`），读图用原生**。
  这个分工建议可以直接写进团队的 AI 助手提示词。

**支持形态**（同一套核心，四种接入方式）：

| 接入方式 | 命令 / 配置 |
| --- | --- |
| DeepSeek Harness 插件 | `dsh plugin --profile <profile> add ./aura-basetools-<版本>.tgz` |
| MCP 服务（Codex / Claude Code / Cursor / 任何 MCP 客户端） | `codex mcp add aura -- aura basetools mcp`、`claude mcp add aura -- aura basetools mcp`，或写入 `mcpServers` |
| 命令行 | `aura basetools read --file <路径> --mode map`、`aura basetools edit --file <路径> --hunks '<JSON>'` |
| 一键安装器 | 双击 `一键安装.cmd`（Windows）/ `一键安装.command`（macOS），或 `node aura-basetools/install.mjs --yes` |

## 五、交付、安装、回滚、合规

**交付形态**：一个压缩包（约 230 KB）。解压后：

- **人**：双击 `一键安装.cmd` / `一键安装.command`
- **交给 AI 助手**：把文件夹给它，说"运行 `node aura-basetools/install.mjs --yes --json`"
- **手工/CI**：`npm i -g ./aura-basetools-<版本>.tgz`（或用 `.tgz` 直接做 DSH 插件）

**安装器会自动完成**：复制到用户目录 → 生成 `aura` / `aura-mcp` 两个命令 → 把 MCP 服务注册进
**检测到的**客户端（Codex / Claude Code / Cursor）→ **跑一次真实自检**（命令行取景 + MCP 握手，
核心工具都在才算通过）。

**安全与可逆**：

| 项目 | 说明 |
| --- | --- |
| 写入范围 | 只写用户目录下的安装位置与**被改的配置文件**；不碰系统目录 |
| 配置改动 | 每个被改的配置文件先备份为 `<文件>.bak-aura-<时间戳>` |
| 他人配置 | 若同名条目已存在且不是本安装器写的，**一律不动**，并在输出里说明 |
| 回滚 | `node aura-basetools/install.mjs --uninstall`：只撤它自己加的东西，逐条可查 |
| 预演 | `--dry-run`：先打印"将要做哪些改动"，不落盘 |
| 联网 | **运行时不发起任何网络请求**（安装器仅在你显式传入 URL 时下载安装包） |
| 遥测 | **无**。不上报任何使用数据 |
| 本地数据 | 仅一个本地观测缓存（默认 `~/.aura`，可用环境变量改到临时目录或只读环境） |
| 许可 | MIT |

**兼容性**：纯 Node 实现（≥18，无原生依赖、无平台分支差异），Windows / macOS / Linux 同一套命令。
Windows 已在真机完整验证（安装、注册、回读校验、卸载复原）；macOS 首次建议用命令行安装
（`node aura-basetools/install.mjs --yes`）并在真机确认，之后再用双击方式分发；macOS 首次运行若遇
Gatekeeper 提示，右键 →「打开」即可。

## 七、明确的能力边界

我们把这些写出来，是因为**边界清楚**比"什么都能做"更值得信任：

| 边界 | Aura 的行为 |
| --- | --- |
| 单 `\r`（老式 Mac）行尾 | 明确拒绝，并给出替代做法（不做半对半错的猜测） |
| 二进制文件 | 拒绝读写 |
| 超过 256 KiB 的文件 | 只记观测令牌、不存全文；读后未变不降级，读后又被外部改动时并发闸门**放行并在回执里标注** `unverified_region`（宁可少拦，不误拦） |
| 整份覆写 | 由 `aura_basetools_write` 提供：新建/覆写、BOM 与文件既有行尾保留、事务/undo、覆写默认要求先读过这一版 |
| 读图片 | 不提供（请用原生 `read_image`） |
| 并发闸门的适用范围 | 对"经由本工具观测过的区域"生效；跨进程/跨机器的最后一道防线是写盘时的版本校验 |

## 八、建议的引入方式（三步，风险可控）

1. **预演**：在目标机器上跑 `node aura-basetools/install.mjs --dry-run`，先看它准备改哪些文件。
2. **试点**：选一个仓库，让 AI 助手改文件时优先用 Aura（团队提示词里加一句分工说明），
   同时保留原生工具。观察一周的两项指标：**提交 diff 是否变干净**、**并发/冲突导致的返工是否减少**。
3. **固化**：把分工写进团队提示词与代码规范；需要时用 `--uninstall` 一键回退。

## 附录 A：对照实验的复跑方法（给工程师）

Windows（PowerShell）：

```powershell
$d="$env:TEMP\aura-对照"; New-Item -ItemType Directory -Force $d | Out-Null
# 夹具：带 BOM 的文件 / 混合行尾的文件（第 1、4 行 CRLF）
[System.IO.File]::WriteAllBytes("$d\bom.js",   [byte[]](0xEF,0xBB,0xBF) + [System.Text.Encoding]::UTF8.GetBytes("const a = 1;`nconst b = 2;`n"))
[System.IO.File]::WriteAllBytes("$d\mixed.js", [System.Text.Encoding]::UTF8.GetBytes("const a = 1;`r`nconst b = 2;`nconst c = 3;`nconst d = 4;`r`n"))
Copy-Item "$d\bom.js" "$d\bom.aura.js"; Copy-Item "$d\mixed.js" "$d\mixed.aura.js"

# ① 用原生 read + edit 各改一处（把 const b = 2; 改成 const b = 22;），随后量：
#    字节数、开头 3 字节、CRLF 与 LF 的计数
# ② 用 Aura 做同一个改动：
$aura="<解压目录>\aura-basetools\bin\aura.mjs"; $env:AURA_CACHE_DIR="$d\cache"
node $aura basetools read --file "$d\bom.aura.js" --mode map
node $aura basetools edit --file "$d\bom.aura.js" --hunks '[{"anchor":"const b = 2;","replace":"const b = 22;"}]'
# ③ 对比两组数字：原生应出现 -2 字节且 BOM 消失、整份 CRLF→LF；Aura 应 +1 字节且只有目标行变化
```

macOS / Linux（bash）：

```bash
d=$(mktemp -d)
printf '\xEF\xBB\xBFconst a = 1;\nconst b = 2;\n'            > "$d/bom.js"
printf 'const a = 1;\r\nconst b = 2;\nconst c = 3;\nconst d = 4;\r\n' > "$d/mixed.js"
cp "$d/bom.js" "$d/bom.aura.js"; cp "$d/mixed.js" "$d/mixed.aura.js"
# 同样用原生工具与 Aura 各改一处，再用 `wc -c`、`xxd | head -1`、`file` 及
# `grep -c $'\r'` 对比行尾与 BOM
```

> 说明：原生工具的行为由**宿主产品**实现决定。本文的对照数据来自我们环境中的宿主工具链；
> 同类工具在其它宿主上是否同样做归一化，取决于各自的实现——请用上面的方法在贵方目标环境复跑一次，
> 再据此评估收益。

## 附录 B：术语

| 术语 | 含义 |
| --- | --- |
| 取景（mode） | 读文件时选择"只看符号目录 / 只要接口 / 只看某个窗口 / 只看差异"等，而不是整份读入 |
| 寻址 | 描述"要改哪儿"的方式：符号名、行号区间、该行唯一的词、记忆中的原文 |
| 新鲜度检查（闸门） | 改动前确认"这块区域在你上次读之后没有被别人改过"，被改过就拒绝并提示重读哪几行 |
| 回读校验 | 写盘后把文件读回来，与预期逐字节比较 |
| CAS / 版本校验 | 写盘时携带"我上次看到的文件版本"，版本不符则写入失败（防止覆盖别人的改动） |
| hunks | 一次编辑里的多处修改；Aura 保证它们要么全部成立，要么磁盘完全不变 |
| MCP | Model Context Protocol，AI 助手接入外部工具的标准协议 |
