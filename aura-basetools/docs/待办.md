### 补充（同轮后续）：宿主 peer 与一个真正的假绿

**现象**：改完接线后重启 dsh **直接报错**。根因是两个宿主 peer 包解析不到。

**机制**（值得记住，因为失败发生在重启而不是安装）：DSH 加载器对**绝对路径**的插件直接 `import(路径)`
（`cordis-plugin-loader/lib/index.js:274-282`），于是插件的依赖从**插件自己的位置**向上找：
`<prefix>/node_modules/aura-tools/...` ⇒ `<prefix>/node_modules/`。那里没有 `@deepseek-ai/*`。
而 dsh **只在启动时导入插件模块、不热更新** ⇒ 安装时一切正常，**重启才爆**。

**修复（两处）**：

1. **安装时就接 peer**：新增 `linkHostPeers()`——把 dsh 自带的 `@deepseek-ai/{schemastery,dsh-tools}`
   junction 到 `<prefix>/node_modules/@deepseek-ai/`（只缺时接，不覆写）。宿主位置由 `hostPeerRoots()` **探测**：
   先问 `npm root -g`，再回退常见全局布局与 npx 缓存。
   *第一版是拼路径的（`dirname(node)/../lib/node_modules` 等三个猜法），本机实测全落空——
   这台机器的 node 与 npm 全局根不在同一棵树，所以“全局布局不能拼、要探测”。*
2. **修掉假绿**：`--doctor` 的 `surfaces.dsh.reachable` 原来只是 `patch.every(fs.existsSync)`。
   实测反例：peer 缺失时两个 `index.js` **确实都在**，`existsSync` 全 true，报告说“reachable: true、重启 dsh 生效”，
   而真实结果是启动报 `ERR_MODULE_NOT_FOUND`。现在补上 `loadable`：**同子进程真 `import()` 一次**
   （与安装时的 `importSmoke` 共用），失败时回执点名具体模块与错误码，退出码 2。

实测两向：

```
peer 在位   DSH 加载  : 两个插件都能 import（重启后可用）      体检结论: 全部正常   exit=0
peer 拿走   ⚠ DSH 插件**加载不了**（文件在，但 import 失败）：
            aura-read: ERR_MODULE_NOT_FOUND；aura-edit: …   体检结论: 1 项需要处理  exit=2
```

**顺带发现并修掉的同类问题**：这次改动后真实安装里的 `install.mjs` 又变旧了（`aura.cmd` 的 shim
调的是安装目录里那份，所以 `aura --doctor` 跑的是**旧代码**）——已重装刷新，两份 `install.mjs` 现逐字节相同。

> **开发期注意**：改完 `build/install.mjs` 后若不重装，`aura --doctor` / `aura --version` 会继续跑旧代码，
> 而它的输出看不出这件事（版本号、构建戳都 “对”）。目前靠人记得——这一条应该做成自动检查。

### 给 dsh / AuraPolaris 那条线的事实（可以转达）

`aura-tools` 的依赖声明是**正确**的：`peerDependencies` 两个包均为 `"*"`、且
`peerDependenciesMeta` 标了 `optional: true`（因为 DSH 面与独立 CLI 面是同一个包，CLI 面不需要它们）。
真正值得转达的是**加载器的后果**：

> 按绝对路径加载插件时，插件的 peer 必须在**插件自己的 node_modules 里可达**，
> 而 dsh 只在启动时导入插件模块、不热更新 ⇒ 缺 peer 的失败会在**重启**才现形。
> 任何“按绝对路径装插件”的宿主都有这条约束；相应地，宿主的安装/体检工具应当做**真 import 冒烟**，
> 而不是 `fs.existsSync`。

**验收**：`install-test` **43 → 46**（新增 I7 报可加载、I8 peer 缺失不再说全部正常、I9 退出码 2）。

**真实依据来自用户的一问**：“为什么这里会有预算呢？你怎么敢预判用户要读写的文件大小？”
三个数字必须分开看：

| 数字 | 性质 |
|---|---|
| `PRUNE_BUDGET = 8192` | **环境硬上限**。`dsh-compaction-tool-result-pruner` 对超过 8192 字符的工具结果保留 前4096 + marker + 后1024；**实测确认该剪枝不区分 `isError`**（`pruneSession` L149-151 对所有 `tool/result` 一视同仁）。它不是我预判，是我无权改写的约束 → 它的派生（`CONTENT_BUDGET` / `omitted` / `next`）是**披露机制**，实测有效（下游剪枝命中 0/11931）。 |

| `CANDIDATE_LIMIT = 6` / `QUOTE_LIMIT = 400` | 同上，拍值。`QUOTE_LIMIT` 仍有依据（错误会被剪），但 400 与 8192 无换算。 |

`build/upgrade-test.mjs`（159 符号 / **5490 字节**），离 8192 尚有 2702 字节。

**做的**：`directoryHint(source, lang, budget = DEFAULT_HINT_CHARS)`，缺省 **7600**（= 8192 − 信封余量），
按**实际渲染行**逐条填充（不再估算行宽——估算拍大就胀回执、拍小就比旧的还少）；返回 `{symbols, total, shown, truncated}`。

写下“默认字节必须与旧行为等价”这个判据。**那个判据本身是错的**：目标应是在硬上限内
**最大化有用信息**，而不是“输出别变多”——把“字节不增”当约束，就会宁可少给。

不是在问别的问题；**98.7% 发生在同一轮之内**（即调用方不需等任何外部结果就发现拿到的东西不可用）。

> **一条必须先说的测量局限**：`(auto: <mode> — <reason>)` 只在 **488/3,812（12.8%）** 的 auto 回执里出现。
> 其余的回执只有 `version:` 行——写那行的实现与会话/时间都无关联。所以**按模式拆分的数字只有 n=488 的样本**；
> 全量的 46.0% 才是不依赖回执头的那一个。把“总是写回执头”本身当成一条待办（它便宜，且是后续任何测量的前提）。

### 据此修的一处（实测驱动）

`read-core.mjs` 的 `suggestMode` 里，小文件门槛是 `CONTENT_BUDGET * 0.25`（约 **1920 字符**）。
后果：**1920–7492 字符的文件全文明明装得下，`auto` 却给索引**——而索引的价值只随文件变大才上升。
现已改成 `source.length <= CONTENT_BUDGET`（装得下就给全文）。

**实测前后**（同一点上）：

```
 2209 字符 → 修前 map / 修后 full
 4449 字符 → 修前 map / 修后 full
 7489 字符 → 修前 map / 修后 full
15089 字符 → 两次都是 map（装不下，正确）
```

**含义**：在装得下的文件上给索引，付出的是一整轮往返，换来的只是“字节更少”——目标函数把
“最小”当成了目标。这与 T11 里我犯的是同一类错（用字节指标替代“是否有用”）。

### 顺带记下的两个引擎异常（未改，待定）

1. `full` 会在**长达内容预算 3.2 倍**的文件上被选中，然后被截成窗口交付（实测：24,388 字符的 .md，

2. `digest` 仍能在只覆盖源文件 **2.7%**（549/20,397 字符）时被选中。

### 与固定夹具的区别（这是本条的全部意义）

固定夹具只在"我想到的那个扰动"下成立。属性测试的期望值不是人写的，而是
**从扰动前后两份索引各自独立算出来的**（与 T24 的差分测试同一原理）。

三条性质，每条都对应一个真实的失效形态：

| 性质 | 断言 | 对应的失效 |
|------|------|-----------|
| 存续性 | 扰动前能寻到的符号，扰动后**要么仍能寻到、要么它真的不在新内容里了** | 名字还在却寻不到（索引与内容脱节） |
| 跨度可信 | 命中区间在文件内、`start<=end`、且**取出的文本真的含有那个名字** | 跨度错位——`target=` 命中后改的就是那几行 |
| 幂等 | 同一份内容两次解析/寻址结果逐字相同 | 索引带缓存，“缓存与内容不一致”几乎不可能被夹具发现 |

扰动的选择本身有判据：**必须语法合法**（只改缩进量 / 末尾追加注释行 / 把空行换成注释行）。
随机插入乱码会让“寻不到”变成**正确行为**，断言会变成假阳性。
随机源是确定性 LCG——属性测试必须**可重放**，否则红了一次也复现不了。

### 它当场发现的东西（超出本条预期）

一版写的是“扰动后命中数**不下降**”。实测 84 次采样里扰动前只命中 69 次——差距不是回归，
是 `target=` 对**重名符号**本来就歧义。顺着查下去得到一个以前从未量过的数：

```
probes/name-addressing.mjs（本仓 7 文件 / 662 个可寻址符号）
  直接命中 497（75.1%）   需要消歧 165（24.9%，全部 STRUCT_AMBIGUOUS）
  失败里可恢复的：165 / 165（#N 或 near= 都能寻到）
```

而**修复前的回执印的是 `candidates: line undefined, line undefined`**：
符号候选带的是 `startLine`/`enclosing`，而共用的格式化器只读 `line`/`text`——
候选算出来了、却没印出来，且两个 `undefined` 看起来像“真的没有候选”。
那是 **25% 的按名编辑**里模型拿到的全部信息。

修法：格式化器在**一处**归一两种候选形状，并直接给出**可直接用的地址**（`target=<名>#<序号>`）
与消歧写法（`near=<行号>`）——`#N` 的语义就是 `resolveTarget` 里 hits 的 1-based 序号。

## T20　（已完成，编号保留作历史锚点）
**交付记录（已完成）**：新增 `src/locator-lab/atomic-publish-test.mjs`（7 项）并接进 `release-check`。
它把"必须原子发布"从**靠人记得**变成**被测试守着**：

```
8 次原子发布 → 8 个互不相同的版本 / 8 个互不相同的 inode
8 次原地覆写 → 只 2 个不同版本（独立复现了先前那次测量的数字）
rename 覆盖、暂存→覆盖 两条发布路径都换索引
同尺寸内容变化经原子发布可被版本区分；令牌形状与 dsh-fs-local 一致
```

**为什么值得单独立一条**：版本令牌 = `dev:ino:size:mtimeNs:ctimeNs`，而 CAS 之所以成立是因为
**staging + 原子替换换了 inode**，不是因为时间戳（实测原地覆写 8 次有 6 次令牌相同）。
一旦有人为了省一次 rename 改成原地写，陈旧守卫会**静默失效**——不报错、看起来成功。
受控并发实验独立给出了同向旁证：原子发布 400/400 次都换索引；原地覆写 211/400 次令牌完全相同。


**来源**：本轮并发专项实测（做并发设计时验证"版本令牌能否区分两次写"，结果发现了一个前提条件，而不是一个 bug）。

**现状（实测，本机 Windows + NTFS，Node 24）**：

```
原子发布（staging + rename）：6 次写 → 6 个不同版本   ✅
原地写（open r+ / write 同尺寸）：6 次写 → 只 2 个不同版本   ❌ 版本会撞
```

撞的原因：版本令牌 = `dev:ino:size:mtimeNs:ctimeNs`（`dsh-fs-local:143`），而本机 `mtimeNs` 的**实际分辨率约 100 纳秒**——同一刻度内的多次写时间戳完全相同。

**为什么现在没出事**：原子发布**更换 inode**（`rename` 语义，实测 `inode: …87250 → …02256`），而每次发布都是新 inode ⇒ 版本天然唯一、**单调不回退**（ABA 不可能）。承载唯一性的是 **inode**，不是时间戳。

**关键推论（这才是风险）**：一旦有人把写路径改成原地写（例如为了省一次 rename、或为了改小文件性能），
同一刻度内同尺寸的修改会让**旧版本 == 新版本** → `replaceIfVersion` 与 `fs/observed` 的陈旧判定**静默失效**，
表现为"第三方改动看不见"——正是本项目最不能接受的一类失败（静默、且看起来成功）。

**影响**：目前是**潜伏**的：真实代码全走 `writeFileAtomic`（含兜底的 `editText`），所以行为正确。
但**没有任何测试在守这个前提**——它是一个"只能靠人记得"的不变量，而本项目已经因为"靠人记得"栽过好几次
（手写透传清单、两处各写一份 rankSymbols 挑选逻辑）。

**怎么做**：
1. 写一条**回归测试**，直接钉住前提：对同一文件连续 N 次原子写，断言产生 N 个**互不相同**的版本；
   再做反向对照——原地写同尺寸内容，断言它们的版本**也互不相同**（若连原地写都不撞，说明平台分辨率够，
   测试可放宽；若撞了，则该测试成为"必须原子发布"的凭据）。
2. 在 `dsh-fs-local` 的写入路径加一句注释，说明**为什么必须 atomic**（不是因为优雅，而是因为版本唯一性依赖它）。
3. 把本条写进 `docs/aura-vs-内置三件套.md` 的"字节证据"章节，与已有的原子发布说明并列。

**前提与风险**：这是**跨平台可变的**——本机是 Windows/NTFS、`mtimeNs` 约 100ns；
Linux（ext4 纳秒、XFS）与 macOS（APFS 纳秒）可能分辨率不同。T5（macOS/Linux 真机验证）时应**重跑这个实验**，
不要把本机结论当成跨平台事实。

**验收**：① 新回归测试在 Windows 上绿，且它能在"把写路径改成原地写"的变体下**变红**；
② T5 在 macOS/Linux 上复跑同一个实验并记录分辨率；③ 注释与文档到位。

**来源**：并发专项 —— 读码发现已有账本，但不变式错了。本条是**设计**，不是已实测的缺陷。

**现状（读码，基线
引擎**已经有**观测存储：`rememberRead(filePath, version, source, byteOrderMark)`（`read-core.mjs:237`）、
`recallRead`（`:260`）、`createMemoryStore(limit = 8)`（`:188`）、宿主可换的缝 `setObservationStore`（`:224`）。
编辑侧**已经**在规划期做区域级陈旧检查（`aura-edit/index.js:516-522`）：

```js
const observation = latestObservation(target.displayPath)
if (observation !== null) { const conflicts = staleConflicts(observation.source, args.hunks, planned.matches, …) }
```

**问题**：`latestObservation(path)` **按路径取、不问版本**。拿一个**旧版本**的文本去核对**新文件**的区域，
判据本身不成立：那个区域恰好没改动时会误判"没变"，改动时会报"region changed"却不告诉模型偏了多少。

**一句话概括**：一个**按版本索引的账本**，被当成了**按路径索引的有界缓存**（且 `limit = 8`）。
架构方向是对的（观测先于写入、闸门在工具侧），**错的是不变式**。

**要实现的不变式**：

> 一个地址，只能对**它被读到时的那一版**执行。

**怎么做**：
1. 规划编辑时按**当前文件版本**去查账本，而不是取"最新一条"；
2. 命中 ⇒ 用它与当前内容做**行级 diff**，算出**偏移 ±N 行**（`changed` 模式**已经在算这个 diff**，见 `renderChanged`，不新增算法）；
3. 未命中（读发生在别的进程 / 被淘汰）⇒ **明说"没有基准"**，不拿旧基准冒充（现在的代码在 `observation === null` 时会完全放行，并把 `unverified_region: true` 写进回执——这条行为要在设计里明确取舍）。

**影响**：冲突从"写盘被拒（整轮作废）"前移到"定位被拒（当场给出偏移量）"，让**一次重试就能收敛**。
安全性不变（闸门照旧），变的是**发现时机与信息量**。这与 T8、T15 是同一个原理：
闸门已经算出"差在哪"，只是没回给模型。

**前提与风险**：
- **必须先有 T22 的曲线**。这条是唯一有架构风险的改动，值不值得做完全取决于"冲突是否随并发上升"；
  现在只有 `n≈2`（跨会话 <5s 仅 1 对）的一个观测点，按平方律外推**是推导不是实测**。
- `limit = 8` 需重定：按版本索引比按路径占更多内存（唯一的真实成本，常数级）。
- 与 T15 重叠：T15 是"先验证猜想"，本条是"若成立则这么实现"。**T15 做分辨实验，本条做实现**，不要同时开工。

**验收**：构造"读 → 第三方改文件（区域未动 / 区域移位 / 区域改动）三种情形"，断言：
① 区域未动 ⇒ 允许写入；② 区域移位 ⇒ 回报精确偏移（`±N 行`）；③ 区域改动 ⇒ 回报实际内容（与 T8 同形）。
三条都要有**负向对照**（故意把账本换成旧版本，确认会被判出来）。

## T22　（已完成，编号保留作历史锚点）

冲突率曲线 —— **已测量，且结论推翻了本条的预设**。

### 实测（受控实验：N 个写者改同一文件、同一快照、随机提交序、败者重读后恰好重试一次；200 轮/N）

| N | 冲突率 | 一次重试收敛 | 最终合入 |
|---|---|---|---|
| 2 | 50.0% | 100.0% | 100% |
| 4 | 75.0% | 33.3% | 100% |
| 8 | 87.5% | 14.3% | 100% |
| 16 | 93.8% | 6.7% | 100% |
| 32 | 96.9% | 3.2% | 100% |
| 64 | 98.4% | 1.6% | 100% |

**冲突率恰好是 `(N−1)/N`，200 轮零方差**——也就是说这个数字是**我设计的读取/提交重叠调度造出来的**，
不是锁的性质：把读与提交**完全错开**（每个写者在上一个提交之后再读），冲突率在任意 N 下都是 **0%**。
所以"提升并发会引发冲突"这个框架本身就是错的；真正的变量是**重试的时机**。

### 两个被证伪的预设（记下来，因为它改了我的判断）

1. **我以为 C13 区域闸门永不触发**（每次成功写入都会刷新观测存储）。错：只要有编辑**移动了行号**，
   闸门就会触发——因为它比的是**同一批行号**在两份内容里的文本。
2. 我先前把"43 次陈旧失败"当成主要成本。实测表明真正的成本形态是别的（见下）。

### 真正要紧的发现：重试本身是静默损坏的载体

当编辑**改变行数**、而重试又用**行号地址**时，重试会把改动写到**错误的行**上、并且回一句**成功回执**：
实测约 **50% 的轮次**以"内容不是预期合入"结束，每轮约 1.5 行附带损伤。

**加上 `expect` 之后：附带损伤 0.00、100% 干净合入**；而对**不改行数**的编辑，`expect` 是**零成本**的
（收敛率不变）。同一个 `expect` 还把"同区域互相覆写"从静默变成响亮失败（false-success 回执 1 → 0）。

**据此已做的改动**（本轮）：
- `aura-edit` 提示段里 `expect` 从"可以传"改成"**当用 `lines`/`start_line`/`line_cue` 寻址时应当传**"，
  并写明理由是"把静默写错行变成响亮失败"。
- 陈旧回执从"重读那几行，然后重试"改成带**下一步**：`retry with expect set to what you find there`。

**实测背景**：`expect` 当前只占 hunk 的 **21%**；而受害面是坐标型寻址（`lines` 5% + `line_cue` 12%），
`anchor`（32%）是内容型地址、行移位本就不影响它。

### 模型的忠实度与边界（不要过度解读）

**忠实**：真实 `planHunks`（未改动）配真实 filePath 与 `lines` 寻址；真实 CAS 语义（`writeText` +
`replaceIfVersion` → `FS_STALE_VERSION`）；真实 per-path FIFO 锁；真实版本令牌形状；门变体用真实
`staleConflicts`/`latestObservation`。
**模拟**：没有字节落盘（内容是内存字符串、版本是合成的单调时钟 + 递增 inode）；一个事件环上的
离散调度而非 OS 级竞争；无跨进程竞争；未建模 `verifyWriteBack`；写者"思考时间"为零，
所以重试落得比真实 LLM 往返更早。

**真实文件上的旁证**（临时目录）：原子发布 400/400 次都换了文件索引；而**原地覆写**在同尺寸重写下
有 **211/400** 次版本令牌完全相同——所以 CAS 之所以成立，是因为**staging + 原子替换**，不是因为时间戳。
这一条与 T20 独立吻合。
## T23　（已完成，编号保留作历史锚点）
**交付记录（已完成）**：并入 `fresh-judgement-test.mjs`（9 项，入闸）。实测 6 次原地写只产生 **2 个**不同版本

**前提与风险**：Linux（ext4/XFS）与 macOS（APFS）分辨率可能是纳秒级、与 Windows 不同——
**不要把本机结论当跨平台事实**，这正是 T5 要跑真机的原因之一。

**验收**：三平台的分辨率数字各一条；仓库内不存在依赖 mtime 做新鲜度判断的代码（grep 可查）。

⇒ 教训：**"笨"不等于"可以错"**——裁判必须拿得准它声称在量的那个东西。

**来源**：从进化论的"变异已便宜 ⇒ 瓶颈在筛选"推出的一条取舍标准，结合本项目三次测试全绿仍带真 bug 的教训。

**现状（实测）**：本项目已经三次出现"测试全绿但功能不对"，三次的共同形态是**测试与代码共享同一个盲区**：
1. `aura_read` 输出 schema 漏声明 `text` → 每条成功路径被框架拒，而 load-test 从不校验输出形状；

3. 上一轮自指实测：**引擎 10 个顶层函数只认出 2 个**（正则字面量未被当词法类别），而当时 44 扩展名、
   11040 符号的语料测试全过。

**影响**：手写测试的期望值是**人写的**。人写期望值时用的是与实现相同的理解，
所以**双方会同时错**——错得一致，测试就绿。

**怎么做**：对每条能力，找一个**独立的第二实现**当裁判，随机生成输入、断言两者等价：

| 快路径（待测） | 慢路径（裁判） | 断言 |
|---|---|---|
| `target=<name>` 定位 | `lines=[a,b]` 逐行扫描该名字 | 两者给出同一个跨度 |
| `map` 的符号集 | `listSymbols(indexStructure(...))` | 集合相等 |
| `aura_edit` 落盘结果 | 读全文 → `oldString→newString` → 整份写回 | 逐字节相同 |
| `search` 命中行 | 纯 `String.prototype.indexOf` 扫描 | 行号集合相等 |
| `changed` 的行级 diff | 逐行 LCS | 变更区间相同 |

**为什么这条值钱**：它**不需要人写期望值** —— 期望值由两个独立实现互相提供，
因此**测试不可能与代码共享同一个盲区**。这一条同时是 T7…T23 的**验收加固**：
任何一条能力改动，都可以加一条"新旧两路必须一致"的断言。

**与既有测试的关系**：不取代，是**补上"期望值来源"这一层**。既有 21 套继续跑（它们抓回归），
差分测试抓"两边一起错"。

**前提与风险**：
- 两个实现共享同一份底层依赖时，差分就失效（例如都用 `langOf`）——**裁判必须真的独立**，
  最好是一个故意写得笨、写得慢的版本（笨是实现独立性的代价）。
- 随机输入必须来自**真实语料**（`corpus-test` 已有 284 文件可用），否则随机生成的代码会偏。
- 需注意误报：两路对**空白/行尾/BOM** 的处理差异可能是**设计上的**（参见 byte-fidelity 段 F），
  这类差异要白名单化并注明理由，不能直接放宽断言。

**验收**：至少三条差分测试落地（建议：定位跨度、`map` 符号集、落盘字节等价）；
每条都能在"故意改坏快路径"的变体下变红（沿用 `adoption-stats-test` 那种"判据也要被测"的做法）。

### 原始条目（保留作历史锚点：设计与理由）

**来源**：分形的自相似原则 + 日志里模型的行为模式。

**现状（实测）**：模型在反复做同一件事：`read → map → 挑一个名字 → 改`（`map` 占 aura_read 调用的 4%，
`auto` 47%，而 `auto` 在不少大文件上正是选 `map`）。这个模式在**文件层**做得很好，
但**再往上一层是空的**——没有"这个仓库里有什么"的 `map`。

**为什么至今没做（也是它的硬约束）**：`map` 之所以便宜，靠的是"重要性排序 + 预算填充"把 400 符号压到几十行。
放大到仓库规模，**不能是"文件的 map 的 map"**（那会直接爆预算），必须是**换一种粗粒度**：
模块 / 目录 / 入口点 / 依赖方向。

**影响**：探索一个不熟悉的仓库时，模型只能"逐个文件 map"，而每次都要先花一个 `glob`/`ls` 才知道有哪些文件。
这是**重复支付的固定成本**（日志里每个会话开头都有这个形状）。

**怎么做**：
1. 复用已有的选择压力：`fitWithin` + `rankSymbols`，但排序依据从"符号重要性"换成"模块重要性"
   （导出数量、被引用次数、最近修改时间、是否入口）；
2. **必须由 `auto` 驱动，不得是新的必填参数** ——T17 实测：模型的 `mode` 主动选择率极低
   （`map` 4%），它宁愿让工具选。加一个必填的 `scope=repo` 就是在**增加决策成本**，与本项目的取舍相反。
3. 输出形态应是"可追问的目录"：先给模块名 + 一句话职责 + 符号数，并附上"怎么深入"的指令。

**前提与风险**：
- 需要**新的排序依据**（模块重要性），而这是一个新概念——容易变成拍数字。
  建议先用可测量的代理：导出数、被其它文件的 `import` 次数（`references` 已有基础设施）。
- 大仓库下建索引有成本 ⇒ 必须**只在文本层够不到时才算**（沿用 `struct-core` 开头第 3 条设计约束）。
- 与 T17 同样属于"行为类改动"：**先量 `auto` 选它的比例**，再决定是否继续投入。

**验收**：在一个 ≥100 文件的仓库上，断言：① 输出不超信封预算；② 能从中定位到指定模块；
③ 模型在使用它后，**探索阶段的调用次数下降**（与 `adoption-stats` 同一口径，不另起入口）。

## T28　（已完成，编号保留作历史锚点）
**交付记录（已完成）**：`pub const` 的残留形状已在 0.7.1 修好；`var-binding-test.mjs` 与
`fresh-judgement-test.mjs` 已把它升为正向断言（含 `pub unsafe const` 与 `pub const fn` 不被变量规则误收）。

| 写法 | 结果 |
|---|---|
| `const A: i32 = 1` | ✅ |
| `static B: i32 = 1` | ✅ |
| `pub static C: i32 = 1` | ✅ |
| `pub(crate) const D: u8 = 2` | ✅ |
| **`pub const G: i32 = 1`** | ✅（0.7.1 修复） |

**机制（已查明）**：`const` 同时是 Rust 的 `modifiers` 词表成员与规则字面量；`$mods*` 原先只试
「全吃 / 不吃」两档，`pub const G` 要么被吃进修饰符段、要么在 `pub` 上对不上字面量。
修法是把 `$mods*` 改成逐长度回溯（吃 `pub`、留 `const`）。下面“来源”起的段落是修复前的记录，保留作历史锚点。


**来源**：本轮做 T7（变量规则补 `$mods*`）时顺带实测发现的**新形状**，未查明机制。

**现状（实测，Windows + current src）**：

| 写法 | 结果 |
|---|---|
| `const A: i32 = 1` | ✅ `variable:A` |
| `static A: i32 = 1` | ✅ `variable:A` |
| `pub static A: i32 = 1` | ✅ `variable:A` |
| `pub(crate) const C: u8 = 2` | ✅ `variable:C` |
| **`pub const A: i32 = 1`** | ❌ 空 |
| **`pub const B: u8 = 2;`** | ❌ 空 |

差异点很清楚：**`pub` 紧邻 `const` 时失效，紧邻 `static` 却正常**，且 `pub(crate) const` 也正常。
Rust 的 `modifiers` 集合里同时有 `const` 与 `static`，所以"`const` 既是修饰符又是关键字"这一条是首要嫌疑，
但**我没有验证到机制**——探针两次插错位置（见下），最终未取到匹配过程的证据。

**影响**：Rust 里 `pub const` 是**常量公开的惯用写法**，这类符号不可按名寻址 / 不出现在 `map`。
不过：

- 本机**零个 `.rs` 文件**（`E:/workspaces` + 部署 node_modules 全扫），因此**无法量化真实影响**；
- `target=` 对这类符号会 `STRUCT_NOT_FOUND`，属 fail-closed（不会改错地方），只是能力缺失。

**怎么做**：
1. **先取证据**：在 `src/locator-lab/` 下写一个**独立探针脚本**（不要像我这次那样往 `struct-core.mjs` 里插临时代码——
   在一个每小时都被别的会话编辑的文件里插探针，两次都插进了 JSDoc 中间并把文件改成语法错误）。
   探针直接调 `matchRule(tokens, i, rule, lang, pairs, lineAt)`，把 `pub const A` 在各位置的命中打出来；
2. 据证据定位：是 `precededByModifier` 判掉了、还是 `matchPattern` 的 `$mods*` 在没有 `modifiers` 匹配时的行为；
3. 修完在 `var-binding-test.mjs` 的负向段加 `pub const` 用例（现在**故意没加**，因为加了会红）。

**前提与风险**：修法动的是共用规则系统 ⇒ 必须同时验"多修饰符不重复"这条负向不变量（`var-binding-test` 段 2 已有）。
Rust 的 `const`/`static` 基础规则本�轮已加（裸形式有实证收益），本条只是 `pub` 前缀那一种组合。

**验收**：`pub const X: T = v` 与 `pub static X: T = v` 都产出 `variable:X`；`var-binding-test` 补该用例后全绿。
