# 服务化升级设计（从"一键安装"到"可升级"）

> 现状：安装已经服务化（一个 zip，一句话交给 agent 装完，幂等、可撤销、装完自检；双击壳已移除）。
> 但**升级还没服务化**：今天要更新，只能重新发一遍 zip、让对方再装一次。
> 本文回答"怎么把升级也做成服务"，含方案对比、推荐路径、接口、失败矩阵与验收标准。

---

## 一、为什么"装得上"不等于"升得动"

| # | 问题 | 今天的实情 |
| --- | --- | --- |
| 1 | **没有版本发现** | 双方都不知道"装的是哪个版本、有没有更新"。`install.json` 里只有安装时的 version，没有任何比对来源 |
| 2 | **磁盘变了 ≠ 进程换代码** | 实测：改完 `.js`，**正在跑的 DSH 宿主仍执行旧模块**（传 `start_line` 被忽略、退回 `auto`，不报错也不崩）；MCP 服务按会话启动，同理；npm 生态的共识也是"更新成功不改变正在应答的那个进程"（[bantamkit-mcp README](https://www.npmjs.com/package/bantamkit-mcp)） |
| 3 | **配置里是绝对路径** | 注册进 Codex/Claude/Cursor 的是 `node <安装目录>/bin/aura-mcp.mjs`。**换目录就会打断**（本轮搬项目目录时亲身踩过） |
| 4 | **回滚不是一等公民** | 现在只有 `--uninstall`（卸干净），没有"退回上一个版本" |
| 5 | **多面版本偏移** | 同一台机器上，CLI 可以是新版、已开的 MCP 会话是旧版、DSH 宿主还是更旧的版本，而**没有任何地方报告这件事** |
| 6 | **升级中断没有保护** | 直接覆盖安装目录，中断就是"半新半旧"（这正是我们反对的那类失败） |
| 7 | **版本号不足以标识产物** | 实测教训（三套靶场抓到的三条"缺口"都是它）：改了源没重建 `dist/` → `0.4.1` 这个版本号下**同时存在两份不同内容的包**，吃产物的调用方命中旧行为。升级必须能回答的不是"是不是 0.4.2"，而是"**这份字节**是不是我以为的那份" |

## 二、生态给了什么、没给什么

- **给了（可依赖）**：MCP 的 `initialize` 握手就是标准钩子——协商 `protocolVersion`、交换 `capabilities` 与
  `serverInfo`（含版本），见 [MCP Lifecycle](https://modelcontextprotocol.io/specification/2025-03-26/basic/lifecycle)。
  我们的服务已经在这里报 `{name:'aura-tools', version}`（0.4.0 起改为读包清单，不再写死）。
  另：`tools.listChanged` 只用于"进程内工具集会变"，我们是静态工具集，继续声明 `false` 是对的。
- **npm 生态惯例**：`latest`/`beta` 这类 **dist-tag** 充当渠道；`npm i -g pkg@beta` 就是切换渠道。
- **没给**：**没有任何标准替你做升级**——没有"服务端推送新版本"、没有原子交换、没有自动回滚、
  没有"三面一致性"。这些必须在安装器里自己实现。

## 三、四个方案（对比后选一个）

| | A 重新发 zip（现状） | **B 安装器 `--upgrade` + 稳定路径 + 原子交换（推荐）** | C 走 npm 包管理 | D 自托管清单服务 + 客户端轮询 |
| --- | --- | --- | --- | --- |
| 需要什么基础设施 | 无（发文件） | **无**（`--from` 本地包即可）；有 URL 时更好 | npm 公开发布 | 一台服务器 + 发布流水线 |
| 离线可用 | ✅ | ✅（`--from <zip/tgz/目录>`） | ❌ | 半（可缓存） |
| 原子性 | 靠人小心 | **staging + 换名**，中断不半新半旧 | 由 npm 负责 | 同 B |
| 回滚 | 重装旧包 | **`--rollback` 一键退回上一版**（且升级自检失败自动回滚） | 装回旧版本号 | 同 B |
| 三面一致性 | 无 | **`--doctor` 报告三面版本与需重启的面** | 无 | 有 |
| 复杂度 | 0 | 中（约 200 行，无新依赖） | 低但需发布 | 高 |
| 适合 | 一次性交付 | **发给别人的工具、内网、mac 用户** | 已上 npm 的公共工具 | 大规模托管 |

**结论：走 B**，并把 C 当作 B 的一个来源（`--from npm:aura-tools@latest` 之后可加），D 暂不做。

## 四、推荐设计（B）

### 4.1 稳定路径 + 版本目录

```
~/.aura/pkg/
  node_modules/aura-tools/     ← 唯一被注册引用的路径（**永远不变**）
  previous/aura-tools/         ← 上一版（回滚用，只留一份）
  staging/                     ← 解包与预检的落脚点（可随时删）
  bin/{aura,aura-mcp}(.cmd)    ← 壳，指向 node_modules/aura-tools/...
  install.json                 ← 状态（见 4.4）
  .cache/                      ← 观测缓存（可由 AURA_CACHE_DIR 改走）
```

**关键点**：注册进各家客户端的绝对路径指向 `node_modules/aura-tools/...`，升级只换**这个目录的内容**，
配置一字不改 → 问题 3、5 的一半自动消失。

### 4.2 升级算法（staging → 预检 → 原子换名 → 终检 → 失败自动回滚）

```
1  解析来源：--from <zip|tgz|目录|URL> | manifest（P1）
2  下载到 staging/，校验 sha256（有 manifest 时）
3  解包到 staging/aura-tools
4  预检（在 staging 里跑，不碰现网）：
     node staging/aura-tools/bin/aura.mjs read --file <临时文件> --mode map
     以及一次 MCP 握手（initialize + tools/list，必须两个工具都在）
5  版本比对：staging 的 version 与现网相同 → 直接删 staging，报“已是最新”（幂等，不写盘）
6  备份：node_modules/aura-tools → previous/aura-tools（覆盖旧备份）
7  换名：staging/aura-tools → node_modules/aura-tools（同盘 rename）
8  终检：在**最终位置**再跑一次 4 的两步
9  终检失败 → 换回 previous（自动回滚），报明原因 + 保留 staging 供排查
10 写 install.json（version、installedAt、previousVersion、payload 来源、sha256、三面清单）
```

**Windows 注意**（实测过目录被占用的痛点）：换名前检测占用——正在运行的 MCP 服务/DSH 宿主已加载的模块
会让 `rename` 失败。策略：**先试换名；失败则明确报"哪个面正在使用（依据：最近的自检/进程列表）"，
并保持现网版本不动**（staging 留着下次复用）。绝不半换。

### 4.3 命令接口（都支持 `--json`）

| 命令 | 作用 | 退出码 |
| --- | --- | --- |
| `install.mjs --version` | 打印已装版本 + 三面各自版本 | 0 |
| `install.mjs --doctor` | 体检：安装目录完整性（按 sha256 清单）、注册项指向的文件是否存在、MCP 握手、缓存目录可写、三面版本偏移、DSH 补丁路径是否可达 | 0 全好 / 2 有问题（回执列出） |
| `install.mjs --check [--manifest URL\|文件]` | 只比较版本（有 manifest 时才联网），打印“当前/可用/是否可升” | 0 |
| `install.mjs --upgrade --from <来源>` | 走 4.2；同版本 → no-op | 0 / 2 预检失败 / 1 用法错 |
| `install.mjs --rollback` | 从 `previous/` 换回上一版（同样先预检） | 0 |
| `install.mjs --dry-run` | 以上任何动作都可预演 | 0 |

### 4.4 `install.json`（状态文件，升级的依据）

```jsonc
{
  "version": "0.4.2",
  "installedAt": "2026-09-22T…",
  "previousVersion": "0.4.1",
  "installDir": "…/node_modules/aura-tools",
  "binDir": "…/bin",
  "payload": { "source": "file:aura-tools-0.4.2-交付包.zip", "sha256": "…" },
  "files": { "aura-read/index.js": "sha256…", "…": "…" },   // 完整性体检用
  "registrations": [{ "agent": "codex", "file": "…", "action": "added" }],
  "surfaces": {                                              // doctor 用
    "cli": "0.4.2", "mcp": "会话启动时读磁盘", "dsh": "宿主启动时导入模块 → 需重启"
  }
}
```

### 4.5 P1：`manifest.json`（有 URL 就能"检查更新"）

```jsonc
{
  "tool": "aura-tools",
  "channels": {
    "stable": { "version": "0.4.2", "url": "…zip", "sha256": "…", "minNode": "18" },
    "beta":   { "version": "0.5.0-beta.1", "url": "…zip", "sha256": "…" }
  }
}
```
- 渠道用 `--channel beta` 选，默认 `stable`。
- **离线/内网**：`--manifest <本地文件>`，行为完全一样（校验 sha256 后安装）。
- **P2（可选）**：清单与包体加 ed25519 签名；`--verify-key <pubkey>`。默认不签名也能用，签名是加固项。

## 五、失败模式矩阵

| 症状 | 检测方式 | 动作 | 用户看到 |
| --- | --- | --- | --- |
| 下载不完整 / 篡改 | sha256 比对（有 manifest 时） | 中止，不碰现网 | “校验不过：期望 … 实际 …” |
| 解出来的不是我们的包 | `package.json.name !== 'aura-tools'` | 中止 | “包体不对” |
| 新版本预检失败 | staging 里跑 CLI+MCP 自检 | 中止（现网未动） | 自检原始错误 + “现网仍是 0.4.1” |
| 换名时目录被占用（Windows） | rename 抛错 | 现网保持不动，保留 staging | “哪个面在用 + 怎么让开” |
| 终检失败（罕见：换名后才坏） | 最终位置再跑自检 | **自动回滚**到 previous | “已回滚到 0.4.1，原因 …” |
| 回滚也失败 | previous 缺失或预检不过 | 停手，打印两条出路（重装 / 手工） | 明确的两条命令 |
| 升级成功但某个面还在跑旧代码 | `--doctor` 对比版本 / 三面清单 | 提示“重启该面才生效” | “Codex：重开会话；DSH：重启宿主；CLI：已是新版” |

## 六、三面的重启语义（实测，必须写进输出）

| 面 | 升级后何时生效 | doctor 怎么报 |
| --- | --- | --- |
| CLI（`aura`） | **立即**（每次调用读磁盘） | 直接报磁盘版本 |
| MCP（Codex / Claude Code / Cursor） | **新会话**（服务按会话由客户端启动） | 报“已装 X；正在跑的会话仍是启动时的版本，重开会话即生效” |
| DSH 工具（aura_basetools_read / aura_basetools_edit / aura_basetools_write） | **重启 dsh**（宿主启动时导入模块，改文件不热更新） | 报“需重启 dsh”，并给出两个补丁文件路径 |

> 这条是本轮实测出来的（传 `start_line` 被旧模块忽略），所以它不是推测，是行为事实。

## 七、升级必须通过的验收（P0 实现时照这个写测试）

1. **幂等**：同版本 `--upgrade` → 不写盘、报“已是最新”（比对 `install.json` 的 mtime 不变）。
2. **配置零改动**：升级前后，三家客户端的配置文件**逐字节相同**（因为路径稳定）。
3. **中断安全**：在交换前后各杀一次进程 → 磁盘要么完整旧版、要么完整新版；`--doctor` 能识别并在必要时提示 `--rollback`。
4. **自动回滚**：故意喂一个"能解包但自检不过"的包 → 必须回滚，且回滚后 CLI 与 MCP 都可用（旧版本自检通过）。
5. **版本可见**：`--doctor --json` 里三面版本齐全；`serverInfo.version` 与新装版本一致。
6. **离线可升**：全程断网，用 `--from` 本地 zip + `--manifest` 本地清单，升级成功。
7. **不做坏事的证明**：默认**不联网**、**无遥测**、**不后台静默更新**（除非显式开 `--check-url`）。

---

## 八、明确不做（保持"服务化"不等于"偷偷动你的机器"）

- ❌ 后台静默自动更新（会与"正在跑的会话"打架，且用户无从知晓）
- ❌ 遥测/版本上报（要统计就自己看 `--doctor` 输出）
- ❌ 无提示替换正在使用的版本（换名失败就明说，不硬来）
- ❌ 去改 DSH 的 live 补丁来"让升级立即生效"（那是别人的运行中配置；保持"重启生效 + 明说"）
- ❌ 为了升级引入第三方依赖（P0 只用 `node:zlib`/`node:fs`，与安装器一致）
