# aura-tools/fixtures —— 「冻结基准」的存放点

这个目录只放**一样**东西：升级前那一份引擎的逐字节副本，供两个探针的「冻结基准」列
（`failure-replay.mjs` / `success-regression.mjs`）当**对照物**使用。

它存在的唯一理由：**冻结基准必须与现树不同源，而且不能随升级被换掉。**

## 里面是什么

| 路径 | 是什么 |
| --- | --- |
| `frozen-engine-0.6.1-217798da/` | 引擎副本本体（19 个文件，598 264 字节）。逐字节等于下面的「来源」。 |
| `frozen-engine-0.6.1-217798da.json` | 机器读的清单：版本 / 树哈希 / 构建戳 / 19 个文件逐个 sha256 / 来源与取用时刻。探针启动时读它，逐文件核对。 |

## 来历（取用时刻：2026-10-14 23:27 +08:00）

| 项 | 值 |
| --- | --- |
| 版本号 | `0.6.1` |
| 树哈希 | `217798da5117394474de1cebd309bb69338b1986306720ee5c52e8e254a8f61a` |
| 构建戳 | `0.6.1+217798da5117` |
| 取自 | `C:\Users\cxk\.aura\pkg\previous\aura-tools` |
| 那一份是什么 | 安装器的 `--rollback` 对调目标 —— **升级前本机真正在跑的那一份现网** |
| 与现网的关系 | 树哈希与现网（`0.6.1+0d07d8b23ae3`）不同：19 个文件里有 10 个字节不同 |
| 与波 7 读数的关系 | 波 7 的「冻结基准 25 / 327」就是这一份跑出来的 |

树哈希算法与 `build/install.mjs` 同一套：目录下每个普通文件的 `相对路径(正斜杠) → sha256`
按相对路径升序拼成 `名字\0哈希\n`，再取 sha256；构建戳 = `版本+树哈希前 12 位`。
所以这 19 个文件是谁都能独立复算的 —— 不需要相信本文档。

## 为什么放仓库里，而不是继续读安装路径

原来两个探针的「冻结基准」直接读 `C:\Users\cxk\.aura\pkg\node_modules\aura-tools`
（本机正在跑的那份）。这在「基准必须与现树是两份代码」这条判据上是**自相矛盾**的：
那个目录正是升级要覆盖的目标，波 8 把安装副本刷新成现树之后，基准列与现树列当场同源，
两条判据如实打红。同理也不能放 `previous/`：它是 `--rollback` 的对调目标，下一次回滚会被换掉。

于是基准改成一个**不在升级路径上**的固定落点：仓库内的只读副本。升级再跑多少遍，
这里的字节都不动；探针每次跑都会拿它跟清单逐文件核对。

体积不是问题：19 个文件 598 KB，比同目录的 `dist/aura-tools-0.6.1-交付包.zip`（595 KB）
还小一点，而 `dist/aura-tools/` 本身就是同样一份完整包体。分发的面也不受影响 ——
`build/make-bundle.mjs` 只按 `package.json` 的 `files` 白名单拷贝，`fixtures/` 不进包。

## 为什么清单与说明写在副本**外面**

副本目录里**只许有**那 19 个文件。往里塞一个 `PROVENANCE.json` 或 `README.md`，
这个目录的树哈希就不再等于 `217798da5117…`，「逐字节副本」这句话也就没法独立复算了。
所以说明放在 `fixtures/README.md`，清单放在 `fixtures/frozen-engine-0.6.1-217798da.json`，
两者都是副本的**兄弟**，不参与副本的树哈希。

## 维护规则（这一节是给下一次动这个目录的人看的）

1. **绝对不要拿现树去刷新它。** 那样两个探针的「基准与现树同源」判据会红并点名，
   但那是**事后**才发现；这里先说清楚：这个目录的字节只能来自一份**已发布、已不再是现树**的包。
2. **要换基准时**（例如引擎再动过一轮、冻结点要往前挪）：从安装器留下的回滚副本
   （`~/.aura/pkg/previous/aura-tools`，或任一份归档下来的旧包）**只读复制**过来，
   换掉目录名里的构建戳，重写同名清单，并在本文件的「来历」表里加一行。
   旧的那一份不要就地覆盖 —— 要么改名留着，要么在提交里留下它的树哈希。
3. **只读。** 没有任何东西该往这个目录里写。探针跑完会拍一次整目录
   mtime/size 快照（`副本目录一个字节没被写` / 判据⑬的最后一条）。
4. 探针对这里只有两种异常态度，都判红并点名，**不静默退化**：
   - 夹具没了 → 红，点名「夹具不存在 + 路径」；
   - 夹具被换成现树（或任何摘要对不上清单的东西）→ 红，点名是哪个文件、
     以及「基准与现树同源」。

## 独立复算（不相信本文档时）

清单里记着 19 个文件逐一的 sha256；逐个对一遍就等于验完了整棵树
（相对路径集合 + 逐文件哈希 ⇒ 树哈希）。在仓库根跑：

```powershell
node -e "const fs=require('fs'),p=require('path'),c=require('crypto');const m=JSON.parse(fs.readFileSync('aura-tools/fixtures/frozen-engine-0.6.1-217798da.json','utf8'));let bad=0;for(const [k,v] of Object.entries(m.files)){const h=c.createHash('sha256').update(fs.readFileSync(p.join('aura-tools/fixtures/frozen-engine-0.6.1-217798da',k))).digest('hex');if(h!==v){console.log('DIFF',k);bad++}}console.log(bad?bad+' files differ':'all '+Object.keys(m.files).length+' files match the manifest')"
```

看不见的交叉核对也在每次跑探针时做：子进程报回的摘要、父进程**独立**算出的摘要、
以及现树同名文件的摘要三行并排打印在 `failure-replay.mjs` 的「冻结基准的来历」块里。
